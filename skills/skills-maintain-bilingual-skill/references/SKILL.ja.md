# バイリンガルスキルのパリティ維持

`SKILL.md`（英語）と `references/SKILL.ja.md`（日本語）の構造的・意味的同期を保つワークフロー。検証ツール駆動の修正でドキュメントドリフトを防ぐ。

## このスキルを使うとき

以下のような場面で使います：
- 既存のバイリンガルスキルにワークフローステップを追加・削除したとき
- validate_skill.py の W1.1（EN/JA H2数不一致）警告を解消したいとき
- 安全重要ボキャブラリの整合性（W3.1/W3.2警告）を確認したいとき
- PRレビューの修正後にEN/JAの両バージョンを見直したいとき
- ENのみの修正をマージした後にJAを同期したいとき
- JAの否定パターン（W3.2）がENの意図と一致しているか確認したいとき
- スキルを公開・昇格する前に構造パリティを監査したいとき

---

## 依存関係

- `uv` — `validate_skill.py` 実行に使うPythonランナー（`uv run python ...`）
- `skills/skill-quality-validation/scripts/validate_skill.py` — バリデータスクリプト（リポジトリ内に既存）
- `grep` / `Select-String` — セクション数とステップ数のカウントに使用

## 関連スキル

## コア原則

1. **構造優先** — セクション見出しとステップ数を合わせてから本文を比較する（基礎と型）
2. **字義より意味** — JAは「なぜ？」の説明を拡張してよい。EN/JAは語数ではなく意図で一致させる（ニュートラル）
3. **バリデータをガードレールに** — `validate_skill.py` はEN版から実行し、警告より先にカテゴリ失敗を修正する（継続は力）
4. **安全ボキャブラリの整合** — 削除/delete、認証/auth はリスクを持つ言葉。W3.1用語は必ず相互確認（基礎と型）
5. **最小デルタ** — パリティ達成に必要な最小変更のみ。関係ない書き換えはしない（余白の設計）

## ワークフロー: EN/JAパリティを維持する

### Step 1: EN版でバリデータを実行する

英語ファイルからクリーンなベースラインを確立する。

```bash
uv run python skills\skill-quality-validation\scripts\validate_skill.py <skill>/SKILL.md
```

出力を確認する点：
- カテゴリ失敗（Structure / Content / Code Quality / Language）→ これを先に修正
- 警告 W1.1（H2数不一致）→ ENのH2数をStep 2のために記録
- 警告 W3.1/W3.2（安全ボキャブラリ、否定パターン）→ 対象行を記録

なぜ？ — ENを先に検証することで、JAとの比較基準を固定できる。EN未修正のままJAを同期すると二重作業になる。

> **Values**: 継続は力（基準を毎回確認する習慣が品質を守る）

### Step 2: パリティチェックリストを作成する

以下のチェックリストでEN/JAを並べて比較する：

| 項目 | EN数 | JA数 | 一致？ |
|------|------|------|--------|
| H2セクション | | | |
| ワークフローステップ（Step N） | | | |
| コードブロック | | | |
| テーブル | | | |

```bash
# H2セクション数をカウント
grep -c "^## " SKILL.md
grep -c "^## " references/SKILL.ja.md

# ステップ数をカウント
grep -c "^### Step" SKILL.md
grep -c "^### Step" references/SKILL.ja.md
```

許容誤差：コードブロック±2、テーブル±1（JAは説明用テーブルを追加してよい）。
ゼロ許容：H2セクション数とステップ数は完全一致が必須。

なぜ？ — バリデータのW1.1はH2数の不一致を検出するが、同一H2内でのステップ増減は検出しない。数値で確認する習慣が silent drift を防ぐ。

> **Values**: 基礎と型（数値で確認できる型を持つ）

### Step 3: 不足セクションを同期する

Step 2 で見つかった不一致ごとに、遅れているファイルにセクションを追加する。

**JAにセクションを追加する場合**：
1. `references/SKILL.ja.md` の対応する位置を特定する。
2. ENセクションを出発点としてコピーする。
3. 見出しと重要フレーズを翻訳し、「なぜ？」の説明を日本語文脈で拡張する。
4. `> **Values**: ...` アノテーション行を保持する。

**JAからセクションを削除する場合**（EN側が削除された場合）：
1. 対応するJAセクションを削除する。
2. 前後のセクション番号が一貫していることを再確認する。

なぜ？ — 構造を揃えることで、読者は言語を問わず同じ知識にアクセスできる。

> **Values**: ニュートラル（構造を揃えることで読者に依存しない文書を作る）

### Step 4: 安全重要ボキャブラリを整合させる（W3.1/W3.2）

バリデータが W3.1 または W3.2 を報告した場合、フラグが立った用語を相互確認する。

**W3.1 — JAの安全ボキャブラリ**（削除、認証、上書き、移行など）

| JA用語 | 期待されるEN対応語 | 確認点 |
|--------|-----------------|--------|
| 削除 | delete / remove | EN/JAは同じ操作を説明しているか？ |
| 上書き | overwrite | 条件は同一か？ |
| 認証 | authentication / credentials | セキュリティ制約は同等か？ |

**W3.2 — 否定パターン**（しない、不可、禁止など）

JAの否定には対応するEN禁止/注意が必要：

```markdown
✅ EN: "Never edit migration files manually."
✅ JA: "マイグレーションファイルを手動編集しない。"

❌ JA: "本番環境では実行しない。"（ENに対応なし）
修正: ENに追加: "Do not run against production environments."
```

なぜ？ — 安全制約が片方の言語にしかない場合、読者が危険な操作を見落とすリスクがある。

> **Values**: 基礎と型（安全制約は両言語で同等に伝える）

### Step 5: 修正後にバリデータを再実行する

残存する警告が意図的かどうかを確認するためバリデータを再実行する。

```bash
uv run python skills\skill-quality-validation\scripts\validate_skill.py <skill>/SKILL.md
```

バリデータはEN SKILL.md を読み、`references/SKILL.ja.md` を自動的に照合する。
このステップ後に残るW3.x警告は手動判断が必要 — 意図的なフレーズ（ENの説明文にある日本語トリガーフレーズなど）は許容される。

**合格基準**：
- 総合スコア ≥ 88%
- W1.1（H2数不一致）なし
- すべてのW3.x警告がレビュー済みで、修正済みまたは明示的に許容済み

> **Values**: 継続は力（最後の一手まで検証する）

### Step 6: パリティの証跡をコミットに記録する

コミットメッセージに同期内容を明示する：

```text
docs(<skill-name>): sync EN/JA parity

- Add JA equivalent of Step N (mirrors EN addition in commit <sha>)
- Fix W3.1: align 削除 description with EN "remove" semantics
- Validate: 92.3% PASS

Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>
```

なぜ？ — 何を同期したかをコミット履歴に残すことで、後からドリフトの原因を特定できる。

> **Values**: 成長の複利（変更理由を記録することで知識が蓄積される）

## よくある失敗

1. **JAを先に編集してからENを直す**
   対策: 必ずENから始め、ENのベースラインを検証してからJAに反映する。JA先行はパリティギャップを作る。

2. **「なぜ？」を字義通りに翻訳する**
   対策: JAの「なぜ？」は日本語の文脈で拡張してよい。豊かなJAの説明は期待値の範囲内。

3. **W3警告を修正後に再確認しない**
   対策: W3.1/W3.2の問題を修正したら、必ずバリデータを再実行して警告が消えたことを確認する。

4. **JAパリティ修正と同時にEN内容を書き換える**
   対策: パリティ同期とEN内容の改善は別コミットに分ける。

## アンチパターン

### サイレントステップドリフト

**問題**: H2数は一致しているが、既存H2内にステップが追加されてステップ数がずれる。W1.1警告は発火しない。

**修正**: ステップ数（### Step N）をH2数とは別に必ず確認する。パリティチェックリストにステップ数を含める。

### 機械翻訳してそのまま出す

**問題**: ENセクションを機械翻訳してJAに貼り付けると、ドメイン用語、Valuesの漢字、スキル固有の言葉が失われる。

**修正**: 見出しと重要フレーズは手作業で翻訳し、「なぜ？」は日本語の文脈で拡張する。

```markdown
## EN/JAパリティチェックリスト — <skill-name>

- [ ] uv run python skills\skill-quality-validation\scripts\validate_skill.py <skill>/SKILL.md
- [ ] H2数が一致している
- [ ] ステップ数が一致している
- [ ] コードブロック数が±2以内
- [ ] テーブル数が±1以内
- [ ] W3.1用語確認: 削除 / 認証 / 上書き / 移行
- [ ] W3.2否定確認: しない / 不可 / 禁止
- [ ] 修正後バリデータ再実行: スコア >= 88%
- [ ] コミットメッセージに同期内容を記録
```

### バリデータ警告リファレンス

| 警告 | 意味 | 修正方法 |
|------|------|---------|
| W1.1 | EN/JA H2セクション数が異なる | 遅れているファイルに不足セクションを追加 |
| W3.1 | JAに安全ボキャブラリ（削除など） | ENに同じ安全制約があるか確認 |
| W3.2 | JAに否定パターン（しないなど） | ENに対応する禁止/注意があるか確認 |
| W5 | EN SKILL.mdに日本語テキスト | 意図的なトリガーフレーズはOK。そうでないものはJAに移動 |
